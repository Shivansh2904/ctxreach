Not reproduced on Windows with Codex 0.159.2, with a key form shown to
apply. What we saw, as rendered by `codex debug prompt-input` 0.159.2 (the
model was not run), one render per case, fresh `CODEX_HOME` each time:

| Override | Project `.codex/config.toml` sets `project_doc_max_bytes = 1000` | Project instructions rendered |
|---|---|---|
| none (trust unknown) | yes | whole chain: the project config is ignored, as expected for an unknown trust level |
| `config.toml`: `[projects.'<repo>'] trust_level = "trusted"` | yes | cut to 1,000 bytes: the project config applies |
| `config.toml`: `[projects.'<repo>'] trust_level = "untrusted"` | - | none |
| `-c "projects.'<repo>'.trust_level=\"untrusted\""` (dotted, as in the report) | - | whole chain: looks like the leak |
| **control:** the same dotted `-c` form set to `"trusted"` | yes | whole chain: **the project config was not applied**, so the dotted key did not address the project at all |
| `-c "projects={'<repo>'={trust_level=\"trusted\"}}"` (inline table) | yes | cut to 1,000 bytes: this form applies |
| the inline-table form set to `"untrusted"` | - | none |

(`-`: the project config does not matter for that row.)

So in our setup the dotted `-c` key never reached the project entry: set to
"trusted" it did not make Codex honour the project config either. With a
form the control shows does apply, `untrusted` delivered no project
instructions, the same as the `config.toml` route. We tried the dotted key
single-quoted, double-quoted with escaped backslashes, and with forward
slashes.

A trusted control is a cheap way to tell an override that leaks from one
that never matched: if `trust_level = "trusted"` with the same key does not
switch on a project `.codex/config.toml`, the key is not addressing the
project. If the dotted form is meant to work for paths, it may be worth a
warning when a `-c` override matches no known key, since today it fails
silently. (That last point is a suggestion, not something we tested.)
